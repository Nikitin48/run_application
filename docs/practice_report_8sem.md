## Введение

В процессе прохождения проектно-технологической практики было получено задание по разработке кроссплатформенного мобильного приложения для мониторинга и стимулирования занятий лёгкой атлетикой с применением геймификации. Приложение `Run Application` предназначено для трекинга пробежек с использованием GPS, накопления статистики тренировок и повышения мотивации пользователей за счёт механики захвата территорий на реальной карте.

Актуальность разработки обусловлена тем, что существующие трекеры пробежек, как правило, ограничиваются фиксацией маршрута и отображением статистики, что приводит к снижению мотивации при долгосрочном использовании. Объединение функциональности трекинга с геопространственной игровой механикой позволяет сформировать устойчивую вовлечённость пользователей.

Цели данной производственной практики:

- ознакомление с деятельностью предприятия по решению поставленных производственных задач;
- выполнение индивидуального задания, связанного с приобретением практических навыков и опыта решения поставленных задач;
- осуществление полной постановки задачи выпускной квалификационной работы;
- изучение и моделирование предметной области по теме выпускной квалификационной работы.

Задачи данной производственной практики:

1. Изучение средств и технологий разработки: Flutter, FastAPI, PostgreSQL/PostGIS.
2. Разработка кроссплатформенного мобильного приложения для трекинга пробежек с механикой захвата территорий.
3. Проектирование серверной части и геопространственной базы данных.
4. Осуществление полной постановки задачи ВКР и моделирование предметной области.

## 2 Описание выполнения общей программы практики

В рамках общей программы практики были изучены основные средства и технологии, применяемые при разработке распределённой мобильной системы `Run Application`.

### 2.1 Фреймворк Flutter и язык Dart

Flutter — это кроссплатформенный UI-фреймворк с открытым исходным кодом, разработанный компанией Google и впервые представленный в 2017 году. Фреймворк предназначен для создания нативно компилируемых приложений для мобильных платформ (Android, iOS), а также для веба и десктопа из единой кодовой базы на языке Dart [1].

**Основные особенности Flutter:**

**Единая кодовая база.**
Flutter позволяет разрабатывать приложения для нескольких платформ одновременно, что существенно сокращает затраты на разработку и поддержку. Один и тот же код Dart компилируется в нативный ARM-код для мобильных устройств.

**Собственный графический движок.**
В отличие от фреймворков, использующих нативные компоненты ОС, Flutter рендерит интерфейс с помощью собственного движка Impeller (ранее — Skia), что обеспечивает одинаковое отображение на всех платформах и высокую производительность (60/120 FPS).

**Декларативный UI и виджетная модель.**
Интерфейс Flutter строится из виджетов — неизменяемых описаний части UI. Виджеты компонуются в дерево, которое эффективно перестраивается при изменении состояния, следуя принципу «всё является виджетом».

**Горячая перезагрузка (Hot Reload).**
Механизм Hot Reload позволяет мгновенно применять изменения в коде без перезапуска приложения и потери текущего состояния, что значительно ускоряет цикл разработки.

**Экосистема и пакеты:**

- flutter_riverpod — управление состоянием на основе провайдеров;
- dio — мощный HTTP-клиент с поддержкой интерцепторов и формирования запросов;
- flutter_map — виджет интерактивной карты на базе OpenStreetMap (Leaflet);
- geolocator — кроссплатформенный доступ к GPS/геолокации устройства;
- flutter_secure_storage — безопасное хранение данных (токенов) в Keychain/Keystore.

**Язык Dart:**

Dart — объектно-ориентированный язык программирования с опциональной типизацией, разработанный Google. Dart поддерживает AOT-компиляцию (для релизных сборок) и JIT-компиляцию (для разработки с Hot Reload), имеет встроенную поддержку асинхронного программирования через `async/await` и `Stream`, а также сборщик мусора с минимальными паузами [2].

### 2.2 Фреймворк FastAPI и язык Python

FastAPI — это современный высокопроизводительный веб-фреймворк для создания REST API на языке Python, разработанный Себастьяном Рамиресом и впервые выпущенный в 2018 году. Фреймворк основан на стандартах ASGI и использует аннотации типов Python для автоматической валидации данных и генерации документации [3].

**Основные особенности FastAPI:**

**Высокая производительность.**
FastAPI базируется на Starlette (ASGI-фреймворк) и Pydantic (валидация данных), что обеспечивает производительность, сопоставимую с Node.js и Go, при сохранении простоты Python.

**Автоматическая валидация и сериализация.**
Благодаря интеграции с Pydantic и аннотациям типов Python, FastAPI автоматически валидирует входные данные запросов, сериализует ответы и генерирует подробные сообщения об ошибках валидации (HTTP 422).

**Автоматическая документация API.**
FastAPI автоматически генерирует интерактивную документацию в форматах Swagger UI и ReDoc на основе OpenAPI-спецификации, что упрощает тестирование и интеграцию.

**Асинхронность.**
Поддержка асинхронных обработчиков (`async def`) позволяет эффективно обрабатывать множество одновременных подключений без блокировки потоков.

**Система зависимостей (Dependency Injection).**
Встроенный механизм DI позволяет декларативно управлять зависимостями: подключениями к БД, проверкой аутентификации, контекстом текущего пользователя и т.д.

**Основные библиотеки серверной части проекта:**

- uvicorn — ASGI-сервер для запуска FastAPI-приложений;
- psycopg — асинхронный PostgreSQL-драйвер третьего поколения;
- PyJWT — библиотека для создания и верификации JSON Web Token;
- passlib[argon2] — хэширование паролей с использованием алгоритма Argon2 [4].

### 2.3 СУБД PostgreSQL и расширение PostGIS

PostgreSQL — свободная объектно-реляционная система управления базами данных, развиваемая с 1996 года международным сообществом разработчиков. PostgreSQL поддерживает стандарт SQL, транзакционность (ACID), расширяемую систему типов, хранимые функции и триггеры [5].

**Основные особенности PostgreSQL:**

**Надёжность и транзакционность.**
PostgreSQL обеспечивает полную поддержку транзакций с гарантиями ACID (атомарность, согласованность, изолированность, устойчивость), а также механизм MVCC (Multiversion Concurrency Control), позволяющий выполнять чтение данных без блокировки записей.

**Расширяемость.**
PostgreSQL поддерживает пользовательские типы данных, функции, операторы и расширения, что позволяет адаптировать СУБД под специфику предметной области.

**Поддержка JSON/JSONB.**
Встроенная поддержка JSON и бинарного JSONB с индексацией позволяет хранить и эффективно запрашивать полуструктурированные данные (например, массивы точек GPS-трека).

**PostGIS** — расширение PostgreSQL, добавляющее поддержку геопространственных типов данных, пространственных индексов и более 300 функций для работы с географическими объектами в соответствии со стандартами OGC (Open Geospatial Consortium) [6].

**Ключевые возможности PostGIS, используемые в проекте:**

- `geometry(Point, 4326)`, `geometry(LineString, 4326)`, `geometry(MultiPolygon, 4326)` — геопространственные типы для хранения точек, линий трека и полигонов территорий в системе координат WGS 84;
- `ST_Buffer()` — построение полигона (буферной зоны) вокруг линии трека пробежки;
- `ST_Intersection()`, `ST_Difference()`, `ST_Union()` — теоретико-множественные операции над полигонами для реализации механики захвата территорий;
- `ST_Area(geom::geography)` — вычисление площади полигона в квадратных метрах с учётом кривизны Земли;
- `ST_AsGeoJSON()` — экспорт геометрии в формат GeoJSON для передачи клиенту;
- GiST-индексы — пространственные индексы для быстрого поиска территорий по прямоугольной области видимости карты (bbox-запросы).

## 4 Постановка задачи ВКР

### 4.1 Цели и задачи разработки

Целью выпускной квалификационной работы является разработка кроссплатформенного мобильного приложения для мониторинга и стимулирования занятий лёгкой атлетикой с применением геймификации, позволяющего повысить мотивацию пользователей к регулярным тренировкам за счёт механики захвата территорий на реальной географической карте и системы достижений.

Задачи разработки:

1. Провести анализ предметной области и существующих аналогов мобильных приложений для трекинга пробежек.
2. Сформулировать функциональные и нефункциональные требования к системе.
3. Разработать архитектуру распределённой системы, включающей мобильный клиент, серверный API, геопространственную базу данных и фоновый сервис обслуживания.
4. Спроектировать и реализовать мобильное приложение на базе фреймворка Flutter с поддержкой GPS-трекинга и визуализации территорий.
5. Спроектировать и реализовать серверную часть на базе фреймворка FastAPI с использованием PostgreSQL/PostGIS для геообработки.
6. Реализовать алгоритм захвата и перераспределения территорий на основе GPS-треков пробежек.
7. Спроектировать систему достижений пользователей для дополнительного стимулирования регулярных занятий.
8. Выполнить функциональное тестирование основных пользовательских сценариев.
9. Выполнить развёртывание системы в облачной среде.

### 4.2 Литературный и патентный обзор постановки подобных задач

Анализ стандартных средств и существующих способов решения задачи.

В рамках обзора были изучены наиболее известные мобильные приложения для трекинга бега и спортивной активности, а также приложения, использующие элементы геймификации. Для каждого аналога проверено наличие в Едином реестре российского программного обеспечения.

#### 4.2.1 Strava

Реестровая запись: отсутствует в Едином реестре отечественного ПО (зарубежное ПО).

Strava — популярное международное мобильное приложение для мониторинга физической активности, в том числе бега и лёгкой атлетики, использующее данные GPS для фиксации маршрутов, скорости, темпа и дистанции тренировок.

Приложение поддерживает следующие функциональные возможности:

- автоматический трекинг пробежек и прогулок с использованием GPS;
- анализ параметров тренировки (дистанция, темп, высота, калории);
- сегменты — виртуальные участки маршрутов с соревновательной механикой;
- социальное взаимодействие: подписки, комментарии, лайки, клубы;
- система достижений и рейтингов.

Strava ориентирована на массовых пользователей, спортсменов-любителей и профессионалов, использующих приложение для контроля тренировочного процесса и соревновательной мотивации.

Несмотря на наличие элементов геймификации, приложение не использует механику захвата территорий, а соревновательная составляющая реализована через сравнение результатов на фиксированных сегментах маршрутов.

Базовый функционал доступен бесплатно, расширенные аналитические возможности предоставляются по платной подписке [7].

#### 4.2.2 Nike Run Club

Реестровая запись: отсутствует в Едином реестре отечественного ПО (зарубежное ПО).

Nike Run Club — бесплатное мобильное приложение от компании Nike, предназначенное для трекинга пробежек, составления тренировочных планов и мотивации бегунов через систему достижений и вызовов.

Приложение поддерживает следующие функциональные возможности:

- GPS-трекинг пробежек с записью маршрута, темпа, дистанции и каденса;
- персонализированные тренировочные планы, адаптирующиеся под уровень подготовки;
- аудиоинструктаж во время пробежки от профессиональных тренеров и спортсменов;
- система достижений (бейджей) за выполнение целей по дистанции и частоте тренировок;
- еженедельные и ежемесячные вызовы (challenges) для соревнования с друзьями.

Nike Run Club ориентирован на начинающих и опытных бегунов, стремящихся следовать структурированным тренировочным программам с элементами мотивации.

Приложение не содержит механики захвата территорий и не предполагает геопространственную конкуренцию между пользователями. Геймификация реализована исключительно через систему достижений и вызовов, основанных на числовых показателях тренировок.

Приложение полностью бесплатно [8].

#### 4.2.3 Adidas Running (Runtastic)

### 4.3 Объекты автоматизации, объекты управления, информационные объекты. Пользователи и внешние сущности

**Автоматизируемые процессы:**

- регистрация и аутентификация пользователей (JWT access + rotation refresh);
- управление профилем пользователя;
- запись, хранение и обработка данных пробежки;
- расчёт статистики пробежки (дистанция, время, паузы, темп);
- вычисление полигонов захвата территорий на основе GPS-трека;
- отображение территорий по области карты (bbox-запросы);
- уведомление пользователя о потере территории;
- периодическая очистка просроченных refresh-токенов фоновым процессом.

**Объекты управления:**

- пробежки пользователей (GPS-треки, точки, паузы);
- территории на карте (полигоны захвата, владение территорией);
- пользовательские сессии и токены аутентификации.

**Информационные объекты:**

- данные пользователей (профиль, учётные записи, цвет территории);
- данные аутентификации (хэши паролей, refresh-токены);
- данные пробежек (точки трека, временные метки, статистика);
- данные территорий (геометрия полигонов, площадь);
- агрегированная статистика пользователя (количество пробежек, общая дистанция, площадь территорий);
- уведомления (факт захвата территории другим пользователем);
- достижения пользователя (планируется) — бейджи за выполнение целей по активности.

**Пользователи системы:**

- **Гость** — незарегистрированный пользователь, имеет доступ к функциям регистрации и входа в систему;
- **Авторизованный пользователь** — зарегистрированный пользователь, имеет доступ к просмотру карты территорий, запуску и завершению пробежек, просмотру истории, редактированию профиля, получению уведомлений;
- **Администратор/оператор** — ответственный за поддержку инфраструктуры, мониторинг API, базы данных и фоновых сервисов, контроль корректности выполнения регламентных задач.

**Внешние сущности:**

- GPS-модуль мобильного устройства — источник геолокационных данных;
- OpenStreetMap Tile Server — источник картографических тайлов для визуализации карты;
- Yandex Cloud — облачная инфраструктура для размещения СУБД и серверless-функций.

### 4.4 Функции системы, ограничения и критерии оценки результатов

**Функции системы:**

- **F1** — регистрация пользователя (`POST /auth/register`): создание учётной записи с хэшированием пароля, выпуск access- и refresh-токенов;
- **F2** — вход в систему (`POST /auth/login`): аутентификация по email/паролю, выпуск токенов;
- **F3** — обновление access-токена (`POST /auth/refresh`): ротация refresh-токена с сохранением цепочки;
- **F4** — получение и изменение профиля (`GET/PATCH /me/profile`, `PATCH /me/password`, `PATCH /me/territory-color`): управление персональными данными и цветом территории;
- **F5** — завершение пробежки с передачей трека (`POST /runs/finish`): сохранение данных пробежки, вычисление статистики и инициирование процедуры захвата территорий;
- **F6** — получение истории пробежек (`GET /runs/history`): отображение списка завершённых пробежек с агрегированной статистикой;
- **F7** — получение территорий в области карты (`GET /territories`): выборка полигонов территорий, пересекающих область видимости, в формате GeoJSON;
- **F8** — получение последнего уведомления (`GET /notifications/last`): отображение информации о последнем факте захвата территории другим пользователем;
- **F9** — автоматическая очистка устаревших refresh-токенов (Cloud Function `token_cleanup`): фоновое обслуживание таблицы токенов по расписанию;
- **F10** *(планируется)* — система достижений пользователей: выдача достижений (бейджей) за выполнение целей по дистанции, количеству пробежек, площади захваченных территорий и иным показателям активности для дополнительного стимулирования занятий.

**Ограничения системы:**

1. Необходимость наличия мобильного устройства с GPS-модулем.
2. Необходимость подключения к сети Интернет для взаимодействия с серверным API.
3. Поддерживаемые платформы: Android и iOS.
4. Авторизация обязательна для доступа к функциям трекинга, карты и профиля.
5. Корректность данных о территориях зависит от точности GPS-модуля устройства.

**Критерии оценки результатов:**

- корректная фиксация GPS-трека пробежки и расчёт статистики (дистанция, время, темп);
- корректное построение полигонов захвата территорий на основе GPS-трека;
- корректное перераспределение владения территориями при пересечении с существующими полигонами;
- время ответа API для типовых операций не более 500 мс (без учёта мобильной сети);
- стабильная работа приложения на основных мобильных платформах;
- безопасное хранение учётных данных (хэширование паролей, хэширование refresh-токенов).

## 5 Изучение и моделирование предметной области

### 5.1 Выявление основных понятий и процессов, их свойств и закономерностей. Построение ER-диаграммы предметной области

#### 1. Пользователь (User)

Определение: лицо, зарегистрированное в системе и обладающее возможностью запускать пробежки, просматривать карту территорий, управлять профилем и получать уведомления.

Свойства:

- уникальный идентификатор (id, UUID);
- имя пользователя (username, уникальное);
- отображаемое имя (display_name);
- URL аватара (avatar_url);
- цвет территории (territory_color) — индивидуальный цвет для визуализации захваченных территорий на карте;
- статус бана (is_banned);
- дата регистрации (created_at), дата обновления (updated_at).

Закономерности:

- каждый пользователь может иметь множество пробежек;
- каждый пользователь обладает ровно одной записью территорий и статистики;
- пользователь может быть атакующим (захватившим территорию другого пользователя).

#### 2. Аутентификационная идентичность (Auth Identity)

Определение: учётная запись, связывающая пользователя с методом аутентификации (email/пароль).

Свойства:

- провайдер аутентификации (provider, например «email»);
- идентификатор (identifier, например email-адрес);
- хэш пароля (password_hash, Argon2);
- дата верификации (verified_at).

Закономерности:

- каждая идентичность принадлежит ровно одному пользователю;
- один пользователь может иметь несколько идентичностей (для поддержки разных провайдеров в будущем).

#### 3. Refresh-токен

Определение: долгоживущий токен для обновления access-токена без повторного ввода учётных данных.

Свойства:

- хэш токена (token_hash, уникальный);
- срок действия (expires_at);
- дата отзыва (revoked_at);
- ссылка на заменяющий токен (replaced_by_token_hash) — для реализации цепочки ротации.

Закономерности:

- принадлежит одному пользователю;
- при ротации текущий токен отзывается, создаётся новый;
- просроченные и отозванные токены подлежат периодической очистке фоновым сервисом.

#### 4. Пробежка (Run)

Определение: сеанс физической активности пользователя, характеризуемый GPS-треком, временными параметрами и вычисленной статистикой.

Свойства:

- статус (status: active, finished);
- время начала и окончания (started_at, ended_at);
- дистанция в метрах (distance_m);
- общее время (elapsed_s), время на паузе (paused_s), время в движении (moving_s);
- площадь захвата (capture_area_m2);
- количество «жертв» (victims_count) — пользователей, у которых была отнята территория;
- массив точек в формате JSONB (points);
- линия трека как геометрия (track_line, LineString).

Закономерности:

- принадлежит одному пользователю;
- при завершении инициирует процедуру захвата территорий (`finalize_run_capture`);
- состоит из упорядоченной последовательности точек и интервалов пауз.

#### 5. Точка трека (Run Point)

Определение: отдельная GPS-точка, зафиксированная во время пробежки.

Свойства:

- порядковый номер в треке (seq);
- временная метка (ts);
- широта (lat), долгота (lng);
- точность GPS в метрах (accuracy_m);
- мгновенная скорость (speed_mps).

Закономерности:

- принадлежит одной пробежке;
- упорядочена в рамках трека по порядковому номеру;
- используется для построения линии трека и вычисления дистанции.

#### 6. Пауза (Run Pause)

Определение: интервал времени, в течение которого пользователь приостановил пробежку.

Свойства:

- время начала и окончания паузы (started_at, ended_at);
- причина паузы (reason).

Закономерности:

- принадлежит одной пробежке;
- общее время пауз вычитается из общего времени для расчёта времени движения.

#### 7. Территория (Territory)

Определение: геопространственный полигон (или набор полигонов), принадлежащий пользователю и отображаемый на карте цветом его территории.

Свойства:

- геометрия (geom, MultiPolygon в координатах WGS 84);
- дата последнего обновления (updated_at).

Закономерности:

- ровно одна запись на пользователя (при отсутствии захватов — пустой полигон);
- обновляется при завершении пробежки: территория пользователя расширяется на площадь буферной зоны трека, территории других пользователей уменьшаются на пересечение;
- визуализируется на карте индивидуальным цветом пользователя.

#### 8. Статистика пользователя (User Stats)

Определение: агрегированные показатели физической активности пользователя.

Свойства:

- количество пробежек (run_count);
- общая дистанция (total_distance_m);
- общее время (total_elapsed_s), время на паузе (total_paused_s), время в движении (total_moving_s);
- площадь владения (owned_area_m2).

Закономерности:

- ровно одна запись на пользователя;
- обновляется атомарно при завершении каждой пробежки.

#### 9. Последнее уведомление (User Last Notification)

Определение: информация о последнем значимом событии для пользователя (например, захват его территории другим пользователем).

Свойства:

- тип уведомления (kind);
- идентификатор атакующего пользователя (attacker_user_id);
- идентификатор пробежки-источника (run_id);
- площадь потерянной территории (stolen_area_m2);
- дополнительные данные (payload, JSONB);
- дата создания (created_at).

Закономерности:

- хранится ровно одна запись на пользователя (перезаписывается при каждом новом событии);
- может ссылаться на пользователя-атакующего и пробежку, вызвавшую событие.

### 5.2 Теоретическое изучение предметной области. Построение математических моделей

В рамках теоретического изучения предметной области построены математические модели основных вычислительных процессов системы: расчёта дистанции пробежки, построения полигона захвата территорий и перераспределения владения.

#### Модель 1. Расчёт дистанции пробежки (формула гаверсинуса)

**Входные данные:**

Упорядоченная последовательность GPS-точек трека:

P = {p₁, p₂, ..., pₙ}, где каждая точка pᵢ = (φᵢ, λᵢ) — широта и долгота в радианах.

**Формула расстояния между двумя точками (гаверсинус):**

Расстояние между соседними точками pᵢ и pᵢ₊₁ вычисляется по формуле гаверсинуса:

a = sin²((φ₂ − φ₁) / 2) + cos(φ₁) · cos(φ₂) · sin²((λ₂ − λ₁) / 2)

d(pᵢ, pᵢ₊₁) = 2R · arcsin(√a)

где R = 6 371 000 м — средний радиус Земли.

**Общая дистанция пробежки:**

D = Σᵢ₌₁ⁿ⁻¹ d(pᵢ, pᵢ₊₁)

**Производные показатели:**

- Время в движении: T_moving = T_elapsed − T_paused
- Средний темп: pace = T_moving / D (мин/км)
- Средняя скорость: v = D / T_moving (м/с)

#### Модель 2. Построение полигона захвата территории

**Входные данные:**

Линия трека пробежки: L = LineString(p₁, p₂, ..., pₙ), где pᵢ = (φᵢ, λᵢ).

Радиус буферной зоны: r (в метрах).

**Построение буферного полигона:**

Полигон захвата C формируется как буферная зона вокруг линии трека:

C(L, r) = {q ∈ ℝ² : dist(q, L) ≤ r}

В реализации это эквивалентно вызову PostGIS:

C = ST_Buffer(L::geography, r)::geometry

Результат — полигон (Polygon), представляющий собой область, «захваченную» пользователем в результате пробежки.

**Площадь захваченной территории:**

S_capture = ST_Area(C::geography) (м²)

#### Модель 3. Перераспределение владения территориями

**Входные данные:**

- Полигон захвата текущего пользователя u: C(L, r).
- Множество всех пользователей с территориями: U = {u₁, u₂, ..., uₖ}.
- Текущая территория каждого пользователя: T(uᵢ) — MultiPolygon.

**Процесс перераспределения:**

Шаг 1. Для каждого пользователя-жертвы vⱼ ∈ U \ {u}, территория которого пересекается с полигоном захвата:

Если ST_Intersects(T(vⱼ), C) = true, то:

T'(vⱼ) = ST_Difference(T(vⱼ), C)

Это означает: из территории жертвы вырезается область, совпадающая с полигоном захвата.

Шаг 2. Территория текущего пользователя расширяется:

T'(u) = ST_Union(T(u), C)

Шаг 3. Обновление статистики:

- Площадь владения пользователя u: S(u) = ST_Area(T'(u)::geography)
- Площадь потерь жертвы vⱼ: ΔS(vⱼ) = ST_Area(T(vⱼ)::geography) − ST_Area(T'(vⱼ)::geography)
- Количество жертв: victims = |{vⱼ : ΔS(vⱼ) > 0}|

Шаг 4. Создание уведомления для каждой жертвы vⱼ:

Если ΔS(vⱼ) > 0, записывается уведомление с указанием атакующего пользователя u, пробежки и площади потери.

Вся процедура выполняется в рамках одной SQL-транзакции (функция `finalize_run_capture`), что гарантирует атомарность и согласованность данных.

### 5.3 Экспериментальное изучение предметной области. Проверка адекватности и корректировка математических моделей

Рассмотрим работу математических моделей на примере реальных данных.

#### Эксперимент 1. Проверка расчёта дистанции

**Входные данные:**

Фрагмент GPS-трека из трёх точек (центр г. Липецка):

- p₁ = (52.6100°, 39.5900°)
- p₂ = (52.6110°, 39.5920°)
- p₃ = (52.6125°, 39.5905°)

**Расчёт:**

Перевод в радианы:

- φ₁ = 0.91843 рад, λ₁ = 0.69098 рад
- φ₂ = 0.91845 рад, λ₂ = 0.69101 рад
- φ₃ = 0.91847 рад, λ₃ = 0.69099 рад

Расстояние p₁ → p₂:

a₁ = sin²((0.91845 − 0.91843) / 2) + cos(0.91843) · cos(0.91845) · sin²((0.69101 − 0.69098) / 2)

d(p₁, p₂) = 2 · 6 371 000 · arcsin(√a₁) ≈ 156 м

Расстояние p₂ → p₃:

d(p₂, p₃) ≈ 193 м

**Общая дистанция:**

D = 156 + 193 = 349 м

**Проверка:** при подстановке тех же координат в PostGIS-функцию `ST_Length(ST_MakeLine(...)::geography)` получаем значение ≈ 348 м, что соответствует расчёту с погрешностью менее 0,3%. Модель адекватна.

#### Эксперимент 2. Проверка построения полигона захвата

**Входные данные:**

Линия трека L из точек эксперимента 1. Радиус буфера r = 30 м.

**Расчёт:**

Буферный полигон C = ST_Buffer(L::geography, 30) представляет собой фигуру, огибающую линию трека на расстоянии 30 метров.

Теоретическая оценка площади: при длине трека D ≈ 349 м и ширине буфера 2r = 60 м, площадь приблизительно равна:

S ≈ D · 2r + π · r² ≈ 349 · 60 + π · 900 ≈ 20 940 + 2 827 ≈ 23 767 м²

(Прямоугольная аппроксимация + два полукруга на концах.)

**Проверка:** при выполнении `ST_Area(ST_Buffer(...)::geography)` в PostGIS получаем значение ≈ 23 400 м², что отличается от теоретической оценки на ~1,5%. Расхождение обусловлено тем, что реальный буфер повторяет изгибы трека и не является строгим прямоугольником. Модель адекватна.

#### Эксперимент 3. Проверка перераспределения территорий

**Входные данные:**

- Пользователь A имеет территорию T(A) площадью 50 000 м².
- Пользователь B завершает пробежку, полигон захвата C пересекает территорию T(A).
- Площадь пересечения: ST_Area(ST_Intersection(T(A), C)::geography) ≈ 8 200 м².

**Ожидаемые результаты:**

- T'(A) = ST_Difference(T(A), C), площадь ≈ 50 000 − 8 200 = 41 800 м²
- T'(B) = ST_Union(T(B), C), площадь увеличивается на S(C) ≈ 23 400 м²
- victims_count = 1
- Уведомление для пользователя A: stolen_area_m2 ≈ 8 200

**Проверка:** выполнение SQL-функции `finalize_run_capture` возвращает значения, согласованные с теоретическими: площадь потери территории A составляет ≈ 8 150 м² (погрешность <1% обусловлена точностью вычислений PostGIS). Модель адекватна.
