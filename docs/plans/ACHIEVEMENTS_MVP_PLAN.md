# План MVP: система достижений и уровней профиля

Документ фиксирует MVP-подход для внедрения достижений в `Run Application`.

## 1. Цели MVP

- Добавить в приложение коллекционные достижения.
- Добавить уровни профиля.
- Показывать popup после завершения забега, если открылись новые достижения.
- Хранить факт получения достижений в БД.
- Не делать скрытые достижения на первом этапе.
- Не делать отображение прогресса вида `3/5` на первом этапе.

## 2. Что уже есть в проекте

В текущей архитектуре уже есть удобная точка для внедрения достижений:

- `python_backend/app/routers/runs.py`
  - endpoint `POST /runs/finish`
  - после завершения пробежки уже известны `distance_m`, `capture_area_m2`, `victims_count`
- `db/functions.sql`
  - `finalize_run_capture(...)` пересчитывает территорию и статистику
- `user_stats`
  - уже хранит агрегаты пользователя, включая `run_count`, `total_distance_m`, `owned_area_m2`

Это значит, что выдачу достижений лучше запускать сразу после завершения пробежки, когда основные метрики уже посчитаны.

## 3. Границы MVP

### Входит в MVP

- Каталог достижений в БД.
- Таблица полученных достижений пользователя.
- Уровень профиля на основе очков достижений.
- Backend-проверка новых достижений после `finish_run`.
- Возврат новых достижений в ответе API завершения забега.
- Popup во Flutter при открытии новых достижений.
- Отображение уровня профиля и списка достижений в профиле.

### Не входит в MVP

- Скрытые достижения.
- Детальный прогресс по каждому достижению.
- Сезонные достижения.
- Глобальный рейтинг по достижениям.
- Отдельный редактор достижений в админке.

## 4. Основная продуктовая логика

### 4.1 Достижения

- Достижения нужны как коллекция.
- Одно действие может открыть сразу несколько достижений.
- Достижения можно группировать по категориям.
- Достижения имеют название, описание, иконку и количество XP.

### 4.2 Уровни профиля

- Уровень профиля нужен.
- Уровень считается по сумме XP от уже полученных достижений.
- В MVP уровень не зависит напрямую от каждой пробежки.
- В будущем можно расширить модель и добавить XP за активность, но сейчас это не требуется.

### 4.3 Popup после забега

- Если после `finish_run` пользователь получил новые достижения, фронтенд показывает popup.
- Если достижений несколько, popup показывает список всех новых достижений.
- Если вместе с этим повысился уровень профиля, popup дополнительно показывает `Level Up`.

## 5. Модель уровней

### 5.1 Источник XP

Каждое достижение даёт фиксированное количество XP.

Рекомендуемая шкала редкости:

- базовое достижение: `100 XP`
- среднее достижение: `250 XP`
- редкое достижение: `500 XP`
- очень редкое достижение: `1000 XP`

Стартовая таблица уровней для MVP:

| 3 | 700 |
| 4 | 1300 |
| 5 | 2200 |
| 6 | 3400 |
| 7 | 4900 |
| 8 | 6700 |

Примечание:

- В MVP можно хранить только `profile_xp` и вычислять уровень на backend по таблице порогов.
- Таблицу порогов лучше держать в коде backend как константу или в отдельной таблице, если хочется гибкости.

  - суммарная площадь, захваченная пользователем за всё время

Лучшее место для этих полей на MVP: расширить таблицу `user_stats`.

## 9. Предлагаемая схема БД

## 9.1 Таблица определений достижений

Таблица: `achievement_definitions`

Рекомендуемые поля:

- `id uuid primary key`
- `code text unique not null`
- `title text not null`
- `description text not null`
- `category text not null`
- `icon_key text not null`
- `xp integer not null`
- `rule_type text not null`
- `rule_value double precision not null`
- `sort_order integer not null default 0`
- `created_at timestamptz not null default now()`

Пример `rule_type`:

- `run_count_gte`
- `distance_single_gte`
- `distance_total_gte`
- `capture_single_gte`
- `capture_total_gte`
- `captures_count_gte`
- `victims_single_gte`
- `victims_total_gte`
- `owned_area_gte`

## 9.2 Таблица полученных достижений

Таблица: `user_achievements`

Рекомендуемые поля:

- `user_id uuid not null references users(id) on delete cascade`
- `achievement_id uuid not null references achievement_definitions(id) on delete cascade`
- `source_run_id uuid references runs(id) on delete set null`
- `unlocked_at timestamptz not null default now()`

Ключи и ограничения:

- `primary key (user_id, achievement_id)`

Примечание:

- отдельная таблица прогресса на MVP не нужна, потому что прогресс до открытия пока не показывается

## 9.3 Расширение `user_stats`

Добавить поля:

- `successful_captures_count integer not null default 0`
- `total_captured_area_m2 double precision not null default 0`
- `total_victims_count integer not null default 0`
- `profile_xp integer not null default 0`
- `profile_level integer not null default 1`

## 10. Где считать выдачу достижений

Рекомендуемый подход: считать достижения на backend в Python, а не в SQL-триггерах.

Причины:

- условия достижений будут меняться
- в Python удобнее поддерживать каталог правил
- проще тестировать и расширять
- логика будет яснее, чем в наборе SQL-триггеров

## 11. Backend flow

Целевой сценарий после завершения забега:

1. `POST /runs/finish` сохраняет забег.
2. Вызывается `finalize_run_capture(...)`.
3. Обновляется `runs.capture_area_m2`, `runs.victims_count`.
4. Обновляется `user_stats`, включая новые накопительные поля.
5. Backend вызывает `achievement_service.evaluate(user_id, run_id)`.
6. Сервис:
   - загружает текущие метрики пользователя
   - находит все достижения, которые уже выполнены
   - отбрасывает те, которые пользователь уже получил
   - записывает новые в `user_achievements`
   - суммирует XP
   - пересчитывает `profile_xp` и `profile_level`
7. `finish_run` возвращает обычный ответ по забегу плюс новые достижения.

## 15. Риски и замечания

- Самая важная новая метрика для MVP: `total_captured_area_m2`.
  - Без неё нельзя корректно считать накопительные достижения по захваченной площади.
- Нужно различать:
  - `текущая площадь`
  - `суммарно захваченная площадь за всё время`
- Территориальные достижения должны показываться пользователю в `км²`, иначе большие значения в `м²` плохо читаются.
- Одно очень сильное действие может открыть сразу несколько достижений.
  - Это нормально и даже полезно для вау-эффекта popup.

## 16. Итоговое решение для MVP

На первом этапе система должна работать так:

- достижения хранятся в БД
- выдача выполняется после завершения забега
- прогресс до открытия не показывается
- скрытых достижений нет
- уровни профиля считаются от XP достижений
- после новых достижений показывается popup
- в профиле отображаются уровень и коллекция достижений

Это достаточно компактный MVP, который хорошо ложится на текущую архитектуру проекта и при этом оставляет место для дальнейшего расширения.
