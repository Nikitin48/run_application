# План на будущее: укрепление бэкенда (Variant B)

Ниже список улучшений “до прод-качества”, которые можно делать после того, как MVP-цикл уже работает.

## 1) Отдельная БД под проект
- Создать отдельную БД (например `run_app`), вместо использования системной `postgres`.
- Перенести схему и функции (`db/schema.sql`, `db/functions.sql`) в новую БД.
- Обновить `DATABASE_URL` в `python_backend/.env`.

## 2) Честный расчёт distance/moving на сервере
- Считать дистанцию по `run_points` (а не “на доверии” клиенту).
- Исключать интервалы пауз из расчёта moving-time (по `run_pauses`).
- Ввести фильтры:
  - игнорировать точки с плохой `accuracy_m`
  - игнорировать “телепорты” (нереальная скорость/скачки)

## 3) История пробежек (для профиля и дебага)
- Добавить эндпоинты:
  - `GET /runs` (список моих пробежек)
  - `GET /runs/{id}` (детали, включая метрики и статус обработки)
- Опционально: выдача трека (line/points) с ограничениями приватности.

## 4) Нормальный refresh в клиенте (UX)
- В клиенте: авто-refresh access token при 401.
- На бэкенде: лимиты и чистка просроченных refresh tokens (cron/job).

## 5) Производительность выдачи территорий
- Упрощение геометрии по zoom на отдаче (`ST_SimplifyPreserveTopology`).
- Опционально: кэширование/материализация геометрий для низких зумов.

## 6) Очередь задач / ретраи обработки
- Если `finalize_run_capture` станет тяжёлым:
  - вынести в job-очередь (таблица `jobs` или Redis worker)
  - добавить ретраи и мониторинг ошибок.
