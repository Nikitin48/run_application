# Анализ авторизации: фронтенд и бэкенд

Краткий разбор текущей реализации и рекомендации по доработкам.

---

## Что уже хорошо

### Backend
- **JWT access + refresh с ротацией**: при каждом refresh старый токен отзывается (`revoked_at`), выдаётся новый — защита от повторного использования.
- **Хеши паролей**: argon2 (с миграцией со старых bcrypt при логине).
- **Хранение refresh в БД**: token_hash, expires_at, user_agent, ip — можно аудит и отзыв.
- **Единые сообщения об ошибках**: при неверном логине всегда «invalid credentials» (не раскрываем, email или пароль).
- **Бан при логине**: при `is_banned` возвращается 403 «user banned».
- **Смена пароля**: после смены все refresh-токены пользователя отзываются — корректно.

### Frontend
- **Secure storage**: токены в `FlutterSecureStorage`.
- **Авто-refresh при 401**: `TokenInterceptor` при 401 вызывает `/auth/refresh`, подставляет новый access и повторяет запрос; при неудаче очищает хранилище.
- **Роутинг по статусу**: GoRouter редирект на `/login` при неавторизованном и на `/map` при успешном логине.
- **Логин/регистрация в одной форме**: переключение сегментами, единый обработчик ошибок (Dio → `detail`).

## Чего не хватает

### 1. Backend: проверка бана при каждом запросе

**Сейчас:** `current_user_id` в `me.py` только декодирует JWT и возвращает `user_id`. Проверка `is_banned` есть только при логине.

**Проблема:** Забаненный пользователь с ещё действительным access-токеном может продолжать ходить в `/me`, `/runs/finish`, `/notifications/last` до истечения токена.

**Рекомендация:** В `current_user_id` (или в общем зависимом сервисе) после декода токена делать запрос в БД: если `users.is_banned = true` — выбрасывать `403 Forbidden`. Тогда все защищённые эндпоинты сразу перестанут обслуживать забаненного.

---

### 2. Backend: эндпоинт выхода (logout)

**Сейчас:** На фронте при «Выйти» только очищается локальное хранилище токенов. Refresh-токен в БД остаётся действительным до истечения срока.

**Проблема:** Если refresh-токен утёк (например, устройство скомпрометировано), его можно использовать до истечения TTL.

**Рекомендация:** Добавить `POST /auth/logout` с телом `{ "refresh_token": "..." }`. На бэкенде: найти запись по `token_hash`, выставить `revoked_at = now()`. Фронт перед очисткой хранилища вызывает этот эндпоинт (если есть refresh). Так текущая сессия явно инвалидируется на сервере.

---

### 3. Backend: лимиты на логин/регистрацию (rate limiting)

**Сейчас:** Нет ограничения частоты запросов к `/auth/login` и `/auth/register`.

**Проблема:** Возможен перебор паролей (brute force) и массовая регистрация.

**Рекомендация:** Ввести rate limiting для этих эндпоинтов (по IP и/или по email): например, не более N попыток в минуту. Варианты: middleware с in-memory/Redis счётчиком или готовое решение (e.g. slowapi). Для прод-окружения — обязательно.

---

### 4. Backend: лимит активных refresh-токенов на пользователя

**Сейчас:** При каждом логине выдаётся новый refresh и пишется в БД; старые не отзываются. Количество сессий (устройств) не ограничено.

**Проблема:** Рост таблицы `refresh_tokens`, невозможность «выйти везде, кроме этого устройства».

**Рекомендация:** (Уже было в roadmap.) Ограничить число активных refresh-токенов на пользователя (например, 5–10). При превышении удалять самые старые по `created_at` или отзывать все, кроме текущего. Опционально — эндпоинт «завершить все сессии, кроме текущей».

---

### 5. Frontend: синхронизация состояния при неудачном refresh

**Сейчас:** В `TokenInterceptor` при неудачном refresh вызываются `tokenStorage.clear()` и `handler.next(err)`. Состояние `AuthController` не обновляется.

**Проблема:** Пользователь может остаться на экране (например, профиль) с «устаревшей» сессией: токены уже удалены, но UI считает пользователя авторизованным до следующего запроса или перехода.

**Рекомендация:** При очистке токенов после неудачного refresh нужно перевести приложение в состояние «не авторизован» и перенаправить на логин. Варианты:
- Пробросить в приложение событие/колбэк «session expired» и в нём вызвать `AuthController.logout()` (и при необходимости `context.go('/login')`), или
- Дать интерцептору доступ к способу инвалидировать сессию (например, через глобальный ключ Riverpod или callback, переданный в `TokenInterceptor`), и после `clear()` вызывать его.

Тогда после истечения/отзыва refresh пользователь сразу окажется на экране входа.

---

### 6. Frontend: валидация формы до отправки

**Сейчас:** На экране логина/регистрации нет проверки формата email и длины пароля до вызова API.

**Проблема:** Лишние запросы при заведомо неверных данных; хуже UX (ошибка приходит с сервера).

**Рекомендация:** Добавить простую клиентскую валидацию: email (регулярка или пакет типа `email_validator`), пароль не короче 8 символов (и при желании — базовые правила сложности). Показывать сообщения под полями и блокировать кнопку «Войти»/«Зарегистрироваться», пока форма невалидна.

---

### 7. Backend: сложность пароля (опционально)

**Сейчас:** В моделях только `min_length=8`, `max_length=200` для пароля.

**Рекомендация:** При желании усилить политику: проверка на наличие цифр, букв разного регистра или спецсимволов; при несоответствии — 422 с понятным `detail`. Можно вынести правила в конфиг (например, в `settings`).

---

### 8. CORS (если появится web-клиент)

**Сейчас:** В `main.py` нет CORSMiddleware.

**Проблема:** При запросах с другого origin (например, веб-приложение на другом порту/домене) браузер заблокирует запросы.

**Рекомендация:** Если планируется веб-фронт на отдельном домене/порту — добавить FastAPI CORSMiddleware с явным списком разрешённых origins и методов/заголовков. Для только мобильного клиента можно отложить.

## Рекомендуемый порядок внедрения

1. **Backend:** Проверка `is_banned` в цепочке зависимостей для защищённых эндпоинтов.
2. **Backend:** `POST /auth/logout` (принять refresh, выставить `revoked_at`).
3. **Frontend:** Вызов logout API перед очисткой хранилища; синхронизация состояния при неудачном refresh (logout + редирект на логин).
4. **Backend:** Rate limiting на auth-эндпоинты.
5. **Frontend:** Валидация полей на экране входа/регистрации.
6. **Backend:** Лимит количества активных refresh-токенов на пользователя (по roadmap).

После этого авторизация будет соответствовать типичным требованиям к прод-качеству (без учёта 2FA и OAuth, которые можно планировать отдельно).
