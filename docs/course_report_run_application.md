## 4 Введение

Развитие мобильных приложений для массового спорта требует не только учета тренировочной активности, но и формирования устойчивой вовлеченности пользователей. Классические трекеры пробежек, как правило, ограничиваются фиксацией маршрута и показом статистики, что снижает мотивацию при долгосрочном использовании.

Актуальность проекта `Run Application` заключается в объединении функциональности трекинга пробежек с геопространственной игровой механикой. Пользователь, завершая маршрут, получает возможность «захватывать» территории на карте, конкурируя с другими пользователями. Такая постановка задачи требует не только стандартной клиент-серверной схемы, но и корректной обработки пространственных данных, транзакционного обновления владения территориями и асинхронного обслуживания токенов аутентификации.

С практической точки зрения система должна быть распределенной, отказоустойчивой, масштабируемой и безопасной, поскольку включает:
- мобильный клиент (Flutter);
- сервер API (FastAPI);
- сервер данных PostgreSQL/PostGIS;
- отдельный фоновый процесс очистки refresh-токенов (Yandex Cloud Functions).

## 5 Техническое задание на программную систему

### 5.1 Краткое изложение сути проекта

`Run Application` — это распределенная программная система для мобильного трекинга пробежек с механикой захвата территорий. Приложение фиксирует GPS-трек пользователя, отправляет его на сервер, где вычисляется площадь захвата и перераспределяются геозоны владения между пользователями.

### 5.2 Автоматизируемые процессы

- регистрация и аутентификация пользователей (JWT access + rotation refresh);
- управление профилем пользователя;
- запись, хранение и обработка данных пробежки;
- расчет статистики пробежки (дистанция, время, паузы, темп);
- вычисление полигонов захвата территорий (PostGIS);
- отображение территорий по области карты (bbox-запросы);
- уведомление пользователя о потере территории;
- очистка просроченных/отозванных refresh-токенов фоновым процессом.

### 5.3 Основные пользователи

- **Гость:** регистрация, вход.
- **Авторизованный пользователь:** просмотр карты, запуск/завершение пробежек, просмотр истории, редактирование профиля, получение уведомлений.
- **Администратор/оператор:** поддержка инфраструктуры, мониторинг API/БД/FaaS, контроль корректности фоновых задач.

### 5.4 Модель вариантов использования

Диаграмма вариантов использования: `docs/scheme/use_case_diagram.puml`.

Ключевые варианты использования:
- регистрация нового пользователя;
- вход и поддержание пользовательской сессии;
- просмотр карты с территориями;
- запуск и завершение пробежки;
- отправка трека и захват территорий;
- просмотр истории пробежек;
- редактирование профиля;
- получение уведомления о потере территории.

### 5.5 Функции системы

- **F1** — регистрация пользователя (`POST /auth/register`);
- **F2** — вход в систему (`POST /auth/login`);
- **F3** — обновление access-токена (`POST /auth/refresh`);
- **F4** — получение/изменение профиля (`GET/PATCH /me/profile`, `PATCH /me/password`, `PATCH /me/territory-color`);
- **F5** — завершение пробежки с передачей трека (`POST /runs/finish`);
- **F6** — получение истории пробежек (`GET /runs/history`);
- **F7** — получение территорий в области карты (`GET /territories`);
- **F8** — получение последнего уведомления (`GET /notifications/last`);
- **F9** — автоматическая очистка устаревших refresh-токенов (Cloud Function `token_cleanup`).

### 5.6 Нефункциональные требования

- **Производительность:** целевое время ответа API для типовых операций `<= 500 мс` (без учета мобильной сети).
- **Масштабируемость:** горизонтальное масштабирование API, независимое масштабирование БД и FaaS.
- **Надежность:** транзакционность операций захвата территорий, атомарность обновления статистики и уведомлений.
- **Безопасность:** хранение паролей в виде хэшей, JWT-аутентификация, хранение refresh-токенов в виде hash.
- **Совместимость:** мобильные платформы Android/iOS; backend на Python 3.11-3.13.
- **Поддерживаемость:** модульная архитектура клиента и сервера, документированные API и диаграммы.

## 6 Архитектура системы

### 6.1 Введение

Архетип системы — **распределенная клиент-серверная система с геопространственным ядром и выделенным фоновым сервисом**.

Концепция архитектуры:
- мобильный клиент отвечает за UI, сбор GPS и взаимодействие с API;
- backend API реализует бизнес-логику и оркестрирует операции;
- PostgreSQL/PostGIS обеспечивает хранение и геообработку;
- серверless-процесс выполняет регламентную очистку токенов.

Таким образом, в системе присутствуют как минимум два независимо функционирующих процесса:
1) API-приложение FastAPI;  
2) Cloud Function `token_cleanup`.

### 6.2 Логическое представление

Логическая декомпозиция отражена в `docs/scheme/system_class_diagram.puml`.

Ключевые логические подсистемы:
- **Подсистема аутентификации:** регистрация, вход, refresh, доступ к защищенным ресурсам;
- **Подсистема пробежек:** трекинг активности, завершение пробежки, история;
- **Подсистема территорий:** загрузка территорий по bbox, геометрические операции захвата;
- **Подсистема уведомлений:** хранение и показ последнего события «территория отжата»;
- **Подсистема профиля:** персональные данные, пароль, цвет территории.

Взаимодействие подсистем реализуется через REST API и доменные модели запросов/ответов.

### 6.3 Представление разработки

Компонентная структура отражена в `docs/scheme/component_diagram.puml`.

Независимо разрабатываемые компоненты:
- **Flutter-клиент:** feature-модули (`auth`, `map`, `runs`, `histories`, `profile`, `notifications`);
- **Backend API (FastAPI):** маршрутизаторы (`auth`, `me`, `runs`, `territories`, `notifications`), модули `security`, `geo`, `db`;
- **Слой данных:** SQL-схема и функции (`db/schema.sql`, `db/functions.sql`);
- **Фоновый сервис:** `faas/token_cleanup/handler.py`.

Технологии и интерфейсы:
- клиент: Flutter, Dart, Riverpod, Dio;
- сервер: FastAPI, Uvicorn, psycopg;
- хранилище: PostgreSQL 17 + PostGIS 3;
- межкомпонентное взаимодействие: HTTPS/REST(JSON), SQL.

### 6.4 Процессное представление

Процессная структура:
- **P1. Мобильный процесс Flutter-приложения** (UI, геолокация, сетевой обмен);
- **P2. Серверный процесс FastAPI/Uvicorn** (обработка запросов, бизнес-логика);
- **P3. Процесс СУБД PostgreSQL/PostGIS** (хранение, геофункции, транзакции);
- **P4. Фоновый serverless-процесс token_cleanup** (по расписанию).

Основные механизмы межпроцессного взаимодействия:
- `P1 <-> P2`: HTTPS REST;
- `P2 <-> P3`: SQL-запросы и вызовы SQL-функций (`finalize_run_capture`);
- `P4 <-> P3`: периодическая SQL-очистка таблицы `refresh_tokens`.

`P2` и `P4` функционируют независимо, имеют отдельные жизненные циклы и могут разворачиваться/масштабироваться независимо.

### 6.5 Представление развертывания

Диаграмма развертывания: `docs/scheme/deployment_diagram.puml`.

Размещение по узлам:
- **Клиентское устройство (iOS/Android):** Flutter-приложение + доступ к GPS;
- **Узел backend:** FastAPI-приложение (Uvicorn);
- **Облачный узел данных:** Managed PostgreSQL + PostGIS (Yandex Cloud);
- **Облачный serverless-узел:** Cloud Function `token_cleanup`.

Сетевые/прикладные протоколы:
- HTTPS/REST (клиент ↔ backend);
- TCP/IP + SQL (backend/FaaS ↔ PostgreSQL).

### 6.6 Представление данных

Концептуальная модель данных представлена в `docs/scheme/er_diagram_run_application.puml`.

Основные сущности:
- `users`, `auth_identities`, `refresh_tokens`;
- `runs`, `run_points`, `run_pauses`;
- `territories`, `user_stats`, `user_last_notification`.

Ключевые связи:
- пользователь имеет множество пробежек и токенов;
- пробежка состоит из точек и интервалов пауз;
- территория, агрегированная статистика и последнее уведомление — по одной записи на пользователя;
- уведомление может ссылаться на атакующего пользователя и пробежку-источник.

### 6.7 Ключевые сценарии

#### Сценарий S1: Регистрация нового пользователя

Диаграмма последовательности: `docs/scheme/sequence_register_new_user.puml`.

Ход сценария:
1. Пользователь вводит email/пароль/display name в мобильном UI.
2. Клиент отправляет `POST /auth/register`.
3. Backend хэширует пароль, генерирует access/refresh токены.
4. В БД создаются `users`, `auth_identities`, `refresh_tokens`.
5. Клиент сохраняет токены в secure storage и переходит на экран карты.

#### Сценарий S2: Просмотр карты территорий

Диаграмма последовательности: `docs/scheme/sequence_view_map_territories.puml`.

Ход сценария:
1. Клиент получает текущую геопозицию.
2. Формируется `bbox` видимой области карты.
3. Запрос `GET /territories` возвращает GeoJSON с полигонами.
4. Клиент рендерит территории поверх картографической подложки.
5. Опционально запрашивается `GET /notifications/last`.

#### Сценарий S3: Завершение пробежки и захват территорий

Диаграмма последовательности: `docs/scheme/system_sequence_diagram.puml`.

Ход сценария:
1. Пользователь завершает активность, клиент отправляет `POST /runs/finish`.
2. Backend сохраняет пробежку и инициирует SQL-функцию `finalize_run_capture`.
3. PostGIS вычисляет полигоны захвата и выполняет перераспределение владения.
4. Обновляются `territories`, `user_stats`, `user_last_notification`.
5. Клиент получает итоговую статистику и отображает экран результата.
