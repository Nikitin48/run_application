# Чеклист лучших практик по структуре бэкенда

Этот чеклист используется для оценки структуры проекта бэкенда перед детальным ревью кода.

## 1) Архитектура и слои
- Есть понятная точка входа приложения (`main`, `app`, `server`).
- Слои разделены по ответственности: `routers/controllers`, `services`, `repositories/data access`, `models/schemas`.
- Бизнес-логика не размазана по роутерам; роутеры в основном занимаются HTTP-слоем.
- Нет циклических зависимостей между ключевыми слоями.

## 2) Конфигурация и окружения
- Настройки централизованы (например, `settings`/`config` модуль).
- Секреты не захардкожены в коде.
- Есть шаблоны переменных окружения (`env.example*`) для разных окружений.
- Для локального и production-сценариев есть явные инструкции запуска.

## 3) Данные и миграции
- Есть выделенный слой доступа к БД.
- Схема БД и миграции хранятся отдельно и версионируются.
- SQL/ORM-запросы не дублируются в разных местах без необходимости.
- Имена миграций и таблиц/полей консистентны.

## 4) Безопасность
- Аутентификация/авторизация выделены в отдельные модули.
- Валидация входных данных централизована и предсказуема.
- Токены/ключи/креды не попадают в репозиторий.
- Есть базовые защитные практики: ограничение CORS, обработка ошибок без утечки внутренних деталей.

## 5) Тестирование
- Есть отдельная директория тестов.
- Тесты покрывают критичные потоки (auth, core business logic, data access).
- Тесты запускаются независимо от локального состояния окружения.
- Тестовые данные и фикстуры организованы и читаемы.

## 6) Документация и DX
- Есть `README` с быстрым стартом.
- Есть документация по API/основным сценариям.
- Скрипты для частых задач (инициализация, импорт данных, админ-операции) вынесены отдельно.
- Структура каталогов читается без долгого погружения.

## 7) Операционка и деплой
- Есть Dockerfile/compose или эквивалент инфраструктурной сборки.
- Файлы окружений и деплоя отделены от application-кода.
- Логи и мониторинг хотя бы на базовом уровне предусмотрены (или есть явный план).

## 8) Зависимости и гигиена проекта
- Зависимости зафиксированы и минимальны.
- Нет неиспользуемых крупных модулей.
- В проекте нет лишних артефактов в репозитории (локальные кэши, секреты, дампы).

## Шкала оценки
- **Соответствует**: практика реализована и используется системно.
- **Частично соответствует**: есть базис, но есть пробелы/несистемность.
- **Не соответствует**: практика отсутствует или реализована рискованно.
