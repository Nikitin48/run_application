# Очистка refresh-токенов: обоснование, данные, план

Документ объединяет рассуждения, примеры данных и ссылку на план реализации. В конце — **промпт для будущего выполнения задания** (реализация FaaS).

---

## 1. Зачем нужна очистка

- **Рост таблицы:** при каждом логине и каждом refresh добавляется новая строка; старые помечаются `revoked_at`, но не удаляются. Без очистки таблица неограниченно растёт.
- **Производительность:** меньше строк — меньше нагрузка на индексы и VACUUM при запросах по `token_hash` и при выборках по пользователю.
- **Гигиена:** истёкшие и отозванные токены уже не используются; хранить их не обязательно.

**Когда можно обойтись без очистки:** при малой нагрузке (десятки/сотни пользователей) таблица растёт медленно. Очистка не обязательна для корректности логина/refresh — это операционная задача, а не требование для работы приложения.

---

## 2. Структура таблицы `refresh_tokens`

```sql
CREATE TABLE IF NOT EXISTS refresh_tokens (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash text NOT NULL UNIQUE,
  created_at timestamptz NOT NULL DEFAULT now(),
  expires_at timestamptz NOT NULL,
  revoked_at timestamptz,
  replaced_by_token_hash text,
  user_agent text,
  ip inet
);
```

| Колонка | Описание |
|---------|----------|
| `id` | PK |
| `user_id` | Владелец токена |
| `token_hash` | Хэш refresh-токена (в БД хранится только хэш) |
| `created_at` | Когда создана запись |
| `expires_at` | Когда токен истекает (например, created + 30 дней) |
| `revoked_at` | Когда отозван: при refresh старый токен помечается здесь |
| `replaced_by_token_hash` | Хэш нового токена, которым заменили этот |
| `user_agent`, `ip` | Метаданные запроса |

Логика в backend: при **refresh** старый токен не удаляется, а обновляется: `revoked_at = now()`, `replaced_by_token_hash = новый_хэш`. Новая строка с новым токеном вставляется отдельно.

---

## 3. Условие очистки

Удаляем строки, где **хотя бы одно** из условий верно:

- `expires_at < now()` — токен истёк;
- `revoked_at IS NOT NULL` — токен отозван (после rotation).

Оставляем только действующие сессии: `expires_at >= now()` и `revoked_at IS NULL`.

---

## 4. Примеры: когда данные чистятся (удаляются)

### 4.1. Токен отозван при refresh (rotation)

Пользователь сделал refresh — старый токен помечен отзывом.

| id | user_id | token_hash | created_at | expires_at | revoked_at | replaced_by_token_hash |
|----|--------|------------|------------|------------|------------|-------------------------|
| aaa-111 | user-1 | hash_old_abc | 2025-02-01 12:00 | 2025-03-03 12:00 | **2025-02-15 10:00** | hash_new_xyz |

→ **Чистим:** `revoked_at IS NOT NULL`.

### 4.2. Токен истёк, refresh не делали

Пользователь давно не заходил, срок жизни токена вышел.

| id | user_id | token_hash | created_at | expires_at | revoked_at | replaced_by_token_hash |
|----|--------|------------|------------|------------|------------|-------------------------|
| bbb-222 | user-2 | hash_expired | 2025-01-01 00:00 | **2025-01-31 00:00** | NULL | NULL |

→ **Чистим:** `expires_at < now()`.

### 4.3. И истёк, и отозван

| id | user_id | token_hash | created_at | expires_at | revoked_at | replaced_by_token_hash |
|----|--------|------------|------------|------------|------------|-------------------------|
| ccc-333 | user-1 | hash_both | 2025-01-01 | **2025-01-31** | **2025-02-01** | hash_other |

→ **Чистим:** оба условия верны.

### 4.4. Реальный пример из системы

Сырая строка (табуляция):

```
83bb6fca-3c8b-4d90-a02d-0bedd1738223  97904990-a9f8-4b0c-9178-b4aba9e38ae5  91e32d502c34283ade7e76cf809d290e6a050dec85888999ea590ae87a051357  2026-02-25 10:33:52.405 +0300  2026-03-27 10:33:52.000 +0300  2026-02-25 11:04:12.385 +0300  3b61940343c45ff84d82280bd77a165d1fea6085241f70b06f11f56ad188a05e  Dart/3.10 (dart:io)  192.168.1.138
```

Разбор по колонкам:

| Колонка | Значение |
|---------|----------|
| id | 83bb6fca-3c8b-4d90-a02d-0bedd1738223 |
| user_id | 97904990-a9f8-4b0c-9178-b4aba9e38ae5 |
| token_hash | 91e32d50...5157 |
| created_at | 2026-02-25 10:33:52 |
| expires_at | 2026-03-27 10:33:52 |
| revoked_at | **2026-02-25 11:04:12** |
| replaced_by_token_hash | 3b619403...805e |
| user_agent | Dart/3.10 (dart:io) |
| ip | 192.168.1.138 |

Интерпретация: токен создан в 10:33, отозван в 11:04 (~30 минут) — пользователь сделал refresh. Текущая сессия — другая строка с `token_hash = 3b619403...805e`, `revoked_at = NULL`. Эта строка **подлежит очистке** (revoked).

## 5. Примеры: когда данные не чистятся (оставляем)

Единственный вариант — **активная сессия**: токен ещё действителен и не отозван.

| id | user_id | token_hash | created_at | expires_at | revoked_at | replaced_by_token_hash |
|----|--------|------------|------------|------------|------------|-------------------------|
| ddd-444 | user-3 | hash_current | 2025-03-01 08:00 | **2025-03-31 08:00** | **NULL** | NULL |

→ **Не чистим:** `expires_at >= now()` и `revoked_at IS NULL`.

---

## 6. Сводка по вариантам

| expires_at | revoked_at | Действие |
|------------|------------|----------|
| в прошлом | NULL | Чистим (истёк) |
| в прошлом | не NULL | Чистим (истёк и отозван) |
| в будущем | не NULL | Чистим (отозван при refresh) |
| в будущем | NULL | **Не чистим** (активная сессия) |

---

**Начало промпта**

Реализуй очистку refresh-токенов через Yandex Cloud Functions по следующему ТЗ.

**Контекст проекта:**
- Backend: FastAPI, PostgreSQL (Yandex Managed PostgreSQL при release). Подключение к БД через `DATABASE_URL` или отдельные переменные `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_SSLMODE` (для облака нужен `sslmode=require`). Формирование URL описано в `python_backend/app/settings.py` (property `database_url_resolved`).
- Таблица `refresh_tokens`: колонки `id`, `user_id`, `token_hash`, `created_at`, `expires_at`, `revoked_at`, `replaced_by_token_hash`, `user_agent`, `ip`. Схема в `db/schema.sql`.

**Требования к функции:**
1. Среда: Yandex Cloud Functions, Python 3.x. Точка входа: handler с сигнатурой `handler(event, context)`.
2. Подключение к PostgreSQL: читать из env `DATABASE_URL` или собрать URL из `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_SSLMODE` (как в backend). Использовать `psycopg` (или `psycopg2`).
3. Логика: выполнить один раз за запуск:
   ```sql
   DELETE FROM refresh_tokens
   WHERE expires_at < now() OR revoked_at IS NOT NULL
   ```
   Опционально: ограничить число удалений за один запуск (например, 10_000 строк) и логировать это.
4. Логирование: в stdout вывести результат (например, количество удалённых строк). При ошибке — логировать и пробросить/вернуть ошибку.
5. Возврат: структура для логов, например `{"deleted": N}` или `{"ok": true, "deleted": N}`.

**Структура в репозитории:**
- Каталог: `faas/token_cleanup/`.
- Файлы: `handler.py` (точка входа), `requirements.txt`.
- Не хранить пароли и секреты в коде; только чтение из переменных окружения.

Ссылайся на существующие документы.

**Критерии готовности:**
- По документу можно развернуть функцию и настроить таймер-триггер.
- Локально (при наличии тестовой БД и env) можно вызвать handler и убедиться, что удаляются только строки с `expires_at < now()` или `revoked_at IS NOT NULL`; строки с активной сессией не трогаются.
