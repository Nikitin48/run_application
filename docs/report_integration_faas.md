# Отчёт: интеграция Run Application и Yandex Cloud Functions

Краткий отчёт по шаблону «интеграция двух ИС». **Примечание:** в проекте одна основная ИС (Run Application) и один облачный сервис (FaaS), выполняющий фоновую задачу; пункты шаблона адаптированы. Лишнее или нерелевантное помечено **[сократить/объединить]**.

---

## 2. Цель работы, задание

**Цель:** вынести периодическую задачу обслуживания данных (очистка устаревших refresh-токенов в БД) из основного приложения в облачную функцию (FaaS), чтобы не нагружать backend и освоить интеграцию с Yandex Cloud Functions.

**Задание:** спроектировать и реализовать вызов облачной функции по расписанию (cron), которая подключается к той же PostgreSQL, что и основное приложение, и удаляет из таблицы `refresh_tokens` записи с истёкшим сроком или отозванные.

---

## 3. Описание интеграционной задачи

### 3.1. Характеристика ИС №1 (Run Application)

- **Назначение:** мобильное приложение для трекинга пробежек с геймификацией (захват территорий, уведомления). Пользователи регистрируются, логинятся, загружают маршруты; backend считает полигоны и хранит данные в БД.
- **Технологии:** Flutter (клиент), FastAPI (REST API), PostgreSQL + PostGIS (данные, в т.ч. таблица `refresh_tokens`). Релизный контур: Yandex Managed PostgreSQL. Аутентификация: JWT (access) + refresh-токены с ротацией; хэши refresh-токенов хранятся в БД.

### 3.2. Характеристика ИС №2 (облачная функция)

- **Назначение:** сервис для выполнения кода по расписанию или по событию без выделенного сервера (FaaS). В проекте используется одна функция — очистка таблицы `refresh_tokens` от устаревших и отозванных записей.
- **Технологии:** Yandex Cloud Functions (Python 3.12), триггер типа «Таймер» (cron). Функция подключается к той же PostgreSQL (Yandex Managed PostgreSQL) по переменным окружения, выполняет `DELETE` и возвращает JSON с количеством удалённых строк.

### 3.3. Задача интеграции

Связать ИС №1 и ИС №2 через **общее хранилище данных** (PostgreSQL) и **регламентный вызов** функции по расписанию. Основное приложение (ИС №1) не вызывает функцию напрямую; планировщик облака (триггер) раз в сутки инициирует выполнение функции; функция читает/изменяет только таблицу `refresh_tokens`. Таким образом, интеграция — «по данным» (общая БД) и «по регламенту» (таймер).

### 3.4. Ограничения решения

- Функция должна работать в среде Yandex Cloud (сеть, DNS): для подключения к Managed PostgreSQL использован IP хоста БД, т.к. DNS-имя `*.mdb.yandexcloud.net` в среде выполнения функции не резолвится.
- Учётные данные БД передаются через переменные окружения функции; пароль без спецсимволов во избежание искажений в консоли.
- Регламент: только по расписанию (cron), вызов по команде пользователя или по событию из приложения не реализован.

## 4. Проектирование интеграционного решения

### 4.1. Преимущества «обмена сообщениями» для интеграции **[адаптация]**

В данном решении нет отдельной очереди сообщений: **инициация выполнения** — это событие таймера (триггер отправляет вызов функции). Преимущества такого подхода:
- основное приложение не нагружается фоновой задачей;
- масштабирование и отказоустойчивость функции обеспечивает облако;
- единая БД — один источник правды; функция выполняет только регламентную очистку без дублирования логики в backend.

### 4.2. Выбор веб-сервиса / платформы **[адаптация: не «обмен сообщениями», а FaaS]**

Выбран **Yandex Cloud Functions** с триггером **Таймер**: сервис выполнения кода по расписанию (cron). Краткая характеристика: управление через консоль или CLI, среда Python 3.12, таймаут и память настраиваются, переменные окружения для подключения к БД; триггер по cron (например, раз в сутки в 03:00 UTC).

### 4.3. Определение формата данных

- **Вход функции:** вызов по таймеру — служебный payload (пустой или метаданные триггера); содержимое не используется.
- **Выход функции:** JSON, например `{"ok": true, "deleted": N}` или `{"ok": false, "error": "..."}`. По этому ответу и логам можно судить об успешности очистки.
- **Данные в БД:** функция изменяет только таблицу `refresh_tokens` (DELETE по условию `expires_at < now() OR revoked_at IS NOT NULL`). Никакого отдельного формата сообщений между ИС №1 и ИС №2 нет — обмен идёт через общую БД.

### 4.4. Регламент обмена данными

**Периодически по интервалу времени:** один раз в сутки по расписанию (cron), например `0 3 * * ? *` (03:00 UTC). Вызов по команде пользователя или по событию в приложении не предусмотрен.

## 5. Реализация и развёртывание интеграционного решения

### 5.1. Настройка веб-сервиса / FaaS

- В консоли Yandex Cloud создана функция (Python 3.12), загружен код (handler + requirements), указана точка входа `handler.handler`.
- Заданы переменные окружения: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_SSLMODE` (значения соответствуют Managed PostgreSQL).
- Создан триггер типа «Таймер» с выбранным cron-выражением и привязкой к функции (через консоль или CLI: `yc serverless trigger create timer ...`).

### 5.3. Информационная система №2 – общий вид (скриншоты)

### 5.4. Работа интеграционного решения (примеры отправки–получения данных)

- **Пример вызова функции вручную:** в консоли Cloud Functions нажать «Запустить тест» / «Вызвать» с пустым телом запроса. В ответе или в логах — `{"ok": true, "deleted": N}`.
- **Проверка в БД:** до вызова — выполнить `SELECT COUNT(*) FROM refresh_tokens WHERE expires_at < now() OR revoked_at IS NOT NULL`; после вызова — повторить запрос (число должно уменьшиться на N) или проверить, что удалённые записи исчезли.

*При необходимости добавить скриншот ответа функции и фрагмент логов.*

## 6. Выводы об использовании интеграционного решения

- Интеграция основной ИС (Run Application) с облачной функцией (Yandex Cloud Functions) реализована через **общую БД** и **регламентный вызов по таймеру**. Отдельный сервис обмена сообщениями (очередь) не используется.
- Функция успешно подключается к Yandex Managed PostgreSQL (при использовании IP хоста и корректного пароля), выполняет очистку и возвращает результат; триггер по расписанию обеспечивает ежедневный запуск без участия основного приложения.
- Ограничения: зависимость от доступности БД из среды выполнения функции, необходимость хранить учётные данные в настройках функции (или в Lockbox). Для учебного/небольшого проекта решение достаточное; при росте нагрузки можно рассмотреть лимит на число удаляемых строк за один запуск и мониторинг логов.
